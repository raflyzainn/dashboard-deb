DEB Sobat Bumi 2025/2026 · Version 12 · row level security, the PF Series way

The browser reads PocketBase directly, PocketBase decides row by row

Your choice: option 2. Every read that the screens need goes from the browser straight to PocketBase with the person's own token, and PocketBase API rules decide which rows that person may see. The server keeps only what rules cannot do: money rules, uploads and private files, decisions with audit and notification, generated letters with QR, the lampiran, payment, sign in. 1 · Model

Two walls instead of one

Today

  • All collections closed (null rules).
  • Browser talks only to our server; the server checks role and campus in code, then reads and writes with one superuser token.
  • One wall: a bug in an endpoint check can expose another campus.

Version 12

  • Every collection gets list and view rules by role and campus (table below). Create, update and delete stay closed to the browser.
  • The browser reads with the person's PocketBase token (PF Series `createUserPB` on the client side); PocketBase enforces the rules on every row.
  • The server keeps the writes that carry business rules, and still uses the superuser token for those. Two walls: code plus rules.
  • Realtime becomes available: a reviewer sees another reviewer's decision without reloading.

3 · Browser versus server

What moves, what stays

Browser reads PocketBase directly

  • Dashboard and Tahap 1 grid: documents, current versions, bank checks, attachments, approved RAB versions of all funded campuses; the assessment and the automatic checks are computed in the browser with the same pure functions (they move from server code to the shared library).
  • Checklist screen: the campus, its SK award, disbursement, documents with versions, reviews, bank check, RAB version, attachments count; the item panel shows the same data.
  • RAB table: rab_versions and rab_lines.
  • Riwayat sheet: audit rows by context (staff).
  • Notifications, Pengguna list, Tahap 2 list, campus view.
  • Realtime: subscribe to documents and reviews of the open campus; the list on the left updates when a colleague decides.

Server endpoints that stay (superuser token)

  • Sign in: password login, Microsoft callback, session cookie, logout, and now also handing the PocketBase token to the browser.
  • Uploads and files: new versions to R2, streaming a version, the SK scan, the bank check evidence, lampiran PDFs.
  • Decisions: Sesuai, Perlu revisi, Tanpa surat kuasa, SK confirmation, bank result, RAB keputusan: they write reviews, audit rows and notifications together.
  • Typed fields (validation, masking of account numbers in audit), disbursement properties, receipt flags.
  • RAB import and approval, generated letters with QR, lampiran build, payment, users admin, program settings.
  • Public: verification by code, health.

4 · Token flow

How the browser gets and keeps its token

1 · Sign in stays on the server. Password login and the Microsoft callback already receive a PocketBase user token; they set the session cookie and now also return the token to the page. The browser saves it in the SDK's auth store (local storage), as PF Series does.
2 · Reads go straight to PocketBase at deb-api.pertaminafoundation.org with that token. PocketBase applies the rule table. Cross origin is allowed by PocketBase's default settings; rate limits count per real visitor (trusted proxy header is already set).
3 · Refresh. The browser calls authRefresh every 20 minutes and on tab focus; the server session cookie keeps its own 8 hour life. Logout clears both.
4 · Role changes. A campus account moved to another campus, or a role removed, takes effect on the next refresh or reload, since the token carries only the id and PocketBase evaluates rules against the current record.
5 · Risks and what limits them

Honest list

  • Token in browser storage. A script injection could read it. Mitigation: no third party scripts, a content security policy on the site, tokens short (PocketBase users tokens default to 7 days; set 1 day) with refresh.
  • Rules drift from code. The rule table lives in the schema script and is applied by provisioning, next to the role list; a test signs in as a campus account and asserts it cannot list another campus.
  • Typed account numbers are readable by the campus itself. Its own numbers, as on its own bank book. Staff see all, as today.
  • PocketBase must stay reachable from campus networks. Same host that serves the site's API today, behind Cloudflare.
  • More requests per screen. The dashboard makes five list calls instead of one; with 23 campuses that is small. Realtime replaces polling.
6 · Plan

Three steps, each usable on its own

  1. Rules and token (half a day). Rule table in the schema script, provisioning applies it, sign in hands the token to the browser, a shared browser client, the campus test proves isolation. Nothing else changes; the server GETs still work.
  2. Reads move (one day). Dashboard, Tahap 1, checklist screen, RAB table, Riwayat, notifications, Pengguna list read PocketBase directly; assessment and checks move to the shared library; the redundant server GETs are removed.
  3. Realtime (half a day). Subscriptions on the open campus so the list and the card update live.

Tested on a local PocketBase with the seeded Universitas Uji Coba and its two accounts, then provisioned to production.
